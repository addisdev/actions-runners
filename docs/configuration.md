# Configuration Reference

All configuration is optional. On a typical single-host fleet, no variables
need to be set: repos are discovered from runner directories, groups are inferred
from repo names, and the GitHub owner is read from `gh`. The variables below
exist for when a default is wrong, or for advanced setups.

## How to set values

Copy `fleet.env.example` to `fleet.env` in the fleet root and uncomment what
you need:

```bash
cp fleet.env.example fleet.env
```

> **Precedence:** `fleet.env` is sourced by the scripts and **wins** over
> environment variables already in the environment. If you pass
> `FLEET_REPOS='a b' ./runs.sh`, a `FLEET_REPOS=` line in `fleet.env` will
> override it. Comment the line out instead.

Dashboard settings (capacity, autoscaling) are stored in SQLite and editable
from the UI. A value in `fleet.env` seeds the setting on first start but does
not override it once it has been changed in the UI — the UI-stored value wins.
The Capacity tab shows which layer (stored, env, or built-in default) each
value came from.

Restart the daemon after changing `fleet.env`:
```bash
cd dashboard && ./fleetctl.sh restart
```

### Database backups and restore drills

The only file worth backing up regularly is `fleet.db` — it holds run history,
admission events, alert state, and capacity settings. Token files and runner
credentials are separate; back those up only if you need to preserve control
access without regenerating tokens.

```bash
cd dashboard
./fleetctl.sh backup          # online, consistent, mode 0600
./fleetctl.sh stop
./fleetctl.sh restore backups/fleet-YYYYMMDD-HHMMSS.db
./fleetctl.sh start
```

`restore` preserves the current database as `fleet.db.rollback-YYYYMMDD-HHMMSS`
before overwriting. Run this sequence on a schedule (monthly is enough for most
fleets) and after every upgrade that touches schema migrations:

1. `./fleetctl.sh backup`
2. `./fleetctl.sh stop && ./fleetctl.sh restore <that backup> && ./fleetctl.sh start`
3. Confirm `./fleetctl.sh status` and that the Capacity tab loads
4. Check migrations: `sqlite3 fleet.db "SELECT id, applied_at FROM schema_migrations ORDER BY id DESC LIMIT 5;"`

If restore fails, stop again and copy the rollback file back over `fleet.db`.

### Prometheus metrics

`dashboard/lib/metrics.js` renders the live snapshot as Prometheus text format.
Metrics cover collector age/staleness, queue depth and worst age by cause,
runner totals and busy count, admission waits, local and fleet-wide headroom,
autoscale state, and federation host counts.

`fleetd` exposes these at `GET /metrics`. Scrape from the same
bind address as the dashboard (`FLEET_HOST:FLEET_PORT/metrics`) and treat it like
`/api/state`: unauthenticated read access on loopback, review exposure on LAN
bindings. See [Security hardening](security-hardening.md#prometheus-metrics).

### Multi-host rollout

Federated fleets add agent hosts gradually. A safe rollout sequence:

1. **Coordinator first** — `./install.sh coordinator`, set `FLEET_HOST_LABELS`
   to what the coordinator can actually run, `./fleetctl.sh agent-token`, back up
   `fleet.db`.
2. **One agent** — `./install.sh agent` with `FLEET_COORDINATOR`, matching
   `FLEET_AGENT_TOKEN`, and that host's `FLEET_HOST_LABELS`. Leave
   `FLEET_AGENT_ALLOW_COMMANDS=0` until heartbeats appear in the Hosts tab.
3. **Dry-run autoscale** — enable autoscale with dry-run on the Capacity tab;
   confirm placement picks the expected host before allowing live actions.
4. **Remote provisioning last** — set `FLEET_AGENT_ALLOW_REGISTER=1` only on
   hosts you intend to grow. Each agent re-checks local headroom before
   `register.sh` runs; a stale coordinator snapshot cannot override that.
5. **Remote removal separately** — set `FLEET_AGENT_ALLOW_DEREGISTER=1` only
   after drain/restart/register commands and their audit results have been
   exercised. Scale-down remains harmlessly refused without it.

Roll agents one at a time. Two agents with the same `FLEET_HOST_NAME` are confusing
in the Hosts tab; two coordinators pointing at different `fleet.db` files split
history permanently unless both use the PostgreSQL HA mode below.

### Two-replica high availability

Both Macs may run jobs and `fleetd`, but only one process may collect GitHub
state, autoscale, backfill, and reconcile alerts. Set the same managed
PostgreSQL URL on both Macs through a mode-0600 `FLEET_DATABASE_URL_FILE`, and
give them distinct `FLEET_REPLICA_ID` values. PostgreSQL advisory locking elects
one leader; the standby serves the shared dashboard snapshot and automatically
promotes if the leader connection disappears.

Do not also run `dashboard/agent.js` on either HA replica. Each `fleetd` reports
that Mac and executes commands addressed to its own `FLEET_REPLICA_ID`; running
the agent too would duplicate host heartbeats and command consumers.

```bash
printf '%s\n' 'postgresql://fleet:...@db.example/fleet?sslmode=require' \
  > dashboard/.fleet-database-url
chmod 600 dashboard/.fleet-database-url
FLEET_REPLICA_ID=mac-mini ./dashboard/fleetctl.sh install
```

Before starting the second replica, archive and verify the existing history:

```bash
cd dashboard
FLEET_DATABASE_URL="$(cat .fleet-database-url)" npm run migrate:postgres
```

Each replica keeps a local SQLite operational/history cache for low-overhead
analytics; PostgreSQL is authoritative for leadership, current fleet snapshots,
host heartbeats, host commands, settings, and autoscale cooldowns. The migration
archive preserves every SQLite table in PostgreSQL JSONB with row counts and
checksums.

### Warm capacity and pre-warming limits

Adding runners increases **concurrency**, not CPU or memory. The headroom gate
(`FLEET_CEILING`, `FLEET_MAX_TOTAL_RUNNERS`, load and disk checks) refuses new
runners while the host is already busy — it does not throttle jobs already
running. In federation, placement may put a new runner on a remote host with
headroom even when the coordinator is saturated.

Forecast-based **pre-warming** remains off by default and shadow-gated: the
Capacity tab shows burst patterns and cron schedules, but `planPrewarm()` refuses
to act until precision and recall gates pass (see [Capacity design](design/capacity.md)).
Turn **Pre-warm** on from the Capacity settings only after the gate shows green.
Even when enabled, pre-warming is still subject to headroom, per-repo caps, lead
time, per-repo cooldown, and the one-action-per-sweep rule — a predicted burst
does not bypass those limits, and reactive autoscale still wins when work is
already queued or running.

### A note on `FLEET_HOST_LABELS`

Placement refuses any host that does not advertise **every** label a new runner
needs. An unset value therefore does not mean "no constraints", it means the host
advertises none and matches nothing, so every scale-up for a labelled runner is
refused with `missing required label(s): …` — naming a label the machine may well
have served for months. Scale-up is off by default, which is how an empty value
goes unnoticed until the first time autoscale is switched on.

Set it to what the host can actually run. The safe way to derive it is from the
runners already on the host: if a runner there carries `ci` and runs jobs with
it, the host can serve `ci`. Do not add a label for something not installed — a
host advertising `xcode-27` without it does not fail at placement, it fails
halfway through somebody's build.

## Capacity and autoscaling

These live in SQLite and are editable from the Capacity tab without restarting
the daemon. A value in `fleet.env` seeds the setting on first boot.

| Setting | Default | What it does |
|---|---|---|
| `FLEET_CEILING` | `3` | Refuse to add runners while this many jobs are running. |
| `FLEET_MAX_TOTAL_RUNNERS` | `8` | Hard cap on runners per host. |
| `FLEET_LOAD_PER_CORE` | `0.7` | Refuse to add runners above this load-per-core ratio. |
| `FLEET_MIN_FREE_DISK_GB` | `20` | Refuse to add runners below this free-disk threshold. |
| Autoscale on/off | off | Toggle on Capacity tab. |
| Autoscale dry-run | off | Log decisions without acting; toggle on Capacity tab. |
| Provision unserved repos | off | Register a repo's **first** runner when it has self-hosted work queued and no runner at all. Everything else the autoscaler does is a duplicate, which is created by copying a sibling — a repo with no runner has no sibling, so this is a separate path. Requires `FLEET_HOST_LABELS` to be set, since it places a labelled runner. See [Giving a repo its first runner](design/capacity.md#giving-a-repo-its-first-runner). |
| Min queued (sustained) | `600000` ms (10 min) | How long work must wait before sustained-mode scale-up. |
| Scale-up cooldown (sustained) | `1800000` ms (30 min) | Minimum gap between sustained scale-ups for one repo+role. |
| Burst mode | off | Shorter thresholds when several jobs queue for one repo+role at once. |
| Burst min queued jobs | `2` | Queue depth before burst thresholds apply. |
| Burst min queued | `120000` ms (2 min) | Queue wait before burst-mode scale-up. |
| Burst cooldown | `300000` ms (5 min) | Minimum gap between burst scale-ups for one repo+role. |
| Burst max batch | `2` | Most runners to add in one revalidated batch (burst mode only). |
| Idle TTL | `259200000` ms (3 days) | Deregister a duplicate runner idle for this long. Three days rather than hours: a dry run at six hours proposed removing a duplicate that had run 103 jobs and last worked that morning — six hours does not mean unused, it means overnight. See [Capacity and autoscaling](design/capacity.md#the-autoscaler). |
| Pre-warm | off | Add one duplicate ahead of a forecast burst. Requires the shadow gate to pass and obeys the same dry-run switch as autoscale. |
| Pre-warm lead | `3600000` ms (1 h) | Act only when the predicted window starts within this lead time. |
| Pre-warm cooldown | `3600000` ms (1 h) | Minimum gap between pre-warms for one repo. |
| Pre-warm min confidence | `medium` | Accept `medium` or `high` forecast confidence; set to `high` to require cron-backed or doubly-confirmed history. |

## Job admission variables

Used by `hooks/job-started.sh`. Must be in `fleet.env` — the hooks cannot
reach the daemon's database.

| Variable | Default | What it does |
|---|---|---|
| `FLEET_ADMIT_MODE` | `off` | `off` / `observe` / `enforce`. |
| `FLEET_ADMIT_MAX_CONCURRENT` | `3` | Max concurrent jobs across the host. |
| `FLEET_ADMIT_SIMULATOR_MAX_CONCURRENT` | `0` | Optional max for runners matching `FLEET_SIMULATOR_RUNNERS`; `0` disables the extra limit. |
| `FLEET_ADMIT_MAX_WAIT_S` | `600` | Max wait before `FLEET_ADMIT_TIMEOUT_ACTION` takes effect. |
| `FLEET_ADMIT_TIMEOUT_ACTION` | `admit` | `admit` fails open after max-wait; `hold` keeps the host limit strict until the run ends. |
| `FLEET_ADMIT_CANCEL_POLL_S` | `30` | How often a held hook checks whether GitHub has completed or cancelled its run. |
| `FLEET_ADMIT_MIN_FREE_DISK_GB` | `40` | Refuse job (then admit after max wait) below this disk level. |
| `FLEET_ADMIT_POLL_S` | `5` | How often a held job re-checks. |
| `FLEET_ADMIT_MUTEX_TRIES` | `50` | Mutex spin attempts per wait-loop tick in `enforce` mode. |
| `FLEET_ADMIT_SLOT_TTL_S` | `21600` | Slot lease TTL in seconds. |

Eligible enforced waiters are FIFO. A Simulator waiter blocked by its
resource-specific limit does not prevent an unrelated waiter from using free
host capacity. A waiter is removed when its hook exits, and stale entries are
reaped by hook-process liveness.

### Finding a fix agent afterwards

Fix agents run in the Cursor cloud, so they are visible in the Cursor app and on
the web as well as in `dashboard/logs/fixes/`. Two things make them easy to miss:

- Agents started through the SDK are hidden from the default agent list. Use
  **Filter → Source → SDK** to see them.
- They are archived on completion by default, so also enable **Filter → Archived**
  (or set `FIX_ARCHIVE_AGENTS=0` while you are still tuning the rollout).

Archiving is not deletion. Every fix report records the `bc-` agent ID, and that
ID still resolves through `Agent.get(id)` and
`Agent.list({ includeArchived: true })`. Any pull request the agent opened is
unaffected.

**Rollout sequence:**
1. `AUTOFIX_DRY_RUN=1 ./autofix/autofixctl.sh run` — confirm bridge decisions match expectations.
2. Add one repo to `AUTOFIX_FIX_REPOS`.
3. `./autofix/fix.sh --verify` — confirm the credential is working.
4. Remove `AUTOFIX_DRY_RUN`, restart the bridge.
5. Monitor `dashboard/logs/fixes/` for reports.
